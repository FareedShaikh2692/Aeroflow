# AeroFlow — Deployment

## Target architecture

```mermaid
flowchart LR
  U[Browser] -->|HTTPS| V[Vercel<br/>React SPA (static, CDN)]
  U -->|HTTPS + JWT<br/>CORS allow-list| G[Render web service<br/>aeroflow-gateway]
  subgraph Render private network
    G --> A[auth] & F[flight] & P[passenger] & B[booking] & C[checkin] & N[notification] & R[reporting]
  end
  A & F & P & B & C & N & R --> PG[(Render PostgreSQL<br/>schema per service)]
  G & F & B --> KV[(Render Key Value / Redis)]
  A & F & B & C & P & N & R <-->|SASL_SSL| K[(Managed Kafka<br/>Confluent Cloud / Aiven / Redpanda)]
```

The frontend is a static Vite build on Vercel. The backend is a set of long-running JVM services and **must not** run as
Vercel functions; it targets Render (Docker) — any container platform works (Railway, Fly.io, ECS, Kubernetes via `infra/k8s`).

## 1. Frontend → Vercel

Project settings (also encoded in `frontend/vercel.json`):

| Setting | Value |
|---|---|
| Root directory | `frontend` |
| Framework | Vite |
| Install | `pnpm install --frozen-lockfile` |
| Build | `pnpm build` (runs `tsc --noEmit` then `vite build`) |
| Output | `dist` |
| Env var | `VITE_API_BASE_URL=https://<gateway-host>` (Production + Preview) |

`vercel.json` rewrites every non-asset path to `/index.html`, so refreshing deep links such as `/admin/flights/<id>` works,
and adds HSTS/`nosniff`/frame-deny headers and immutable caching for hashed assets.

```bash
cd frontend
npx vercel link                       # choose/create the project, root = frontend
npx vercel env add VITE_API_BASE_URL production
npx vercel --prod
```

## 2. Backend → Render (Blueprint)

`render.yaml` defines the gateway (public web service), seven private services, PostgreSQL and Key Value (Redis).
All images build from `backend/Dockerfile` with `SERVICE=<module>` (Render passes env vars as Docker build args).

1. Create a managed Kafka cluster (Confluent Cloud basic, Aiven, or Redpanda Serverless) and an API key/secret.
2. Render dashboard → **New → Blueprint** → select the repo → fill the prompted values:
   `KAFKA_BOOTSTRAP_SERVERS`, `KAFKA_USERNAME`, `KAFKA_PASSWORD`, `CORS_ALLOWED_ORIGINS=https://<your-app>.vercel.app`.
   `JWT_SECRET` is generated by Render. Services run with `SPRING_PROFILES_ACTIVE=json-logs,cloud-kafka`.
3. Each service uses its own schema in the single database (`DB_SCHEMA` + `currentSchema`), created by Flyway on boot.
4. Copy the gateway URL (e.g. `https://aeroflow-gateway.onrender.com`) into Vercel's `VITE_API_BASE_URL` and redeploy the frontend.
5. Verify: `python3 scripts/smoke_test.py https://aeroflow-gateway.onrender.com` and
   `E2E_BASE_URL=https://<your-app>.vercel.app pnpm --dir frontend e2e`.

> Cost note: eight JVM services need paid instances (~512 MB each) to stay warm; free instances sleep and cold-start slowly.

## 3. Environment variables

| Variable | Services | Required | Notes |
|---|---|---|---|
| `JWT_SECRET` | all except gateway | yes | ≥ 32 bytes, identical across services |
| `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` | data services | yes | `DB_URL` defaults to `jdbc:postgresql://localhost:5432/aeroflow_<svc>` |
| `DB_SCHEMA` | data services | no | schema-per-service mode |
| `REDIS_URL` | gateway, flight, booking | yes | `redis://` or `rediss://` |
| `KAFKA_BOOTSTRAP_SERVERS` | data services | yes | |
| `KAFKA_USERNAME`, `KAFKA_PASSWORD`, `KAFKA_SASL_MECHANISM` | data services | managed Kafka | with profile `cloud-kafka` |
| `KAFKA_TOPIC_REPLICAS` | data services | no | 1 locally, 3 on managed clusters |
| `CORS_ALLOWED_ORIGINS`, `CORS_ALLOWED_ORIGIN_PATTERNS` | gateway | yes | exact Vercel domain; pattern for previews |
| `*_SERVICE_URL` | gateway, flight, booking, checkin | yes | internal service base URLs |
| `PORT` | all | platform | defaults 8080–8087 |
| `JWT_ACCESS_TTL`, `JWT_REFRESH_TTL` | auth | no | `15m`, `7d` |
| `SEED_DEMO_DATA`, `DEMO_PASSWORD` | auth, flight, reporting | no | demo users/flights/synthetic history |
| `CHECKIN_OPENS_HOURS`, `CHECKIN_CLOSES_MINUTES` | checkin | no | `48`, `60` |
| `SPRING_PROFILES_ACTIVE` | all | no | `json-logs` (structured logs), `cloud-kafka` |
| `VITE_API_BASE_URL` | frontend (build time) | prod | gateway origin |

## 4. Health checks

| Endpoint | Purpose |
|---|---|
| `GET /actuator/health` | aggregate (DB, Redis where used, disk) |
| `GET /actuator/health/readiness` | platform readiness / load balancer |
| `GET /actuator/health/liveness` | restart decisions |
| `GET /actuator/prometheus` | metrics scrape |

## 5. Docker Compose (local or single VM)

```bash
cp .env.example .env        # fill JWT_SECRET, DB_PASSWORD, POSTGRES_PASSWORD, GRAFANA_ADMIN_PASSWORD
cd infra && docker compose --env-file ../.env up -d --build
# UI http://localhost:3000 · API http://localhost:8080 · Prometheus :9090 · Grafana :3001 (dashboard "AeroFlow - Service Overview")
```

## 7. Production readiness checklist
- [ ] `SEED_DEMO_DATA=false` (or keep for the demo environment only)
- [ ] Strong `JWT_SECRET` stored in the platform secret store
- [ ] `CORS_ALLOWED_ORIGINS` set to the exact production domain
- [ ] Managed Kafka with replication factor 3; DLT topics monitored
- [ ] Database backups / PITR enabled
- [ ] Alerts on 5xx rate, p95 latency, outbox backlog (`aeroflow_outbox_pending`) and consumer lag
